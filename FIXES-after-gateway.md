# Что исправить после гейтвея

Список по итогам осмотра проекта 2026-10-24 (состояние: `main` на 7e6e201, `release/gateway` на a6809d7, PR #30 открыт).
Файл не для мерджа в `main`: по правилу из `CLAUDE.md` заметки такого рода в репозитории не хранятся. Прочитай, сделай правки отдельными PR, ветку удали.

Порядок ниже — по важности.

## 1. Противоречие в правилах про блокеры тикетов

`CLAUDE.md`, пункт про тикеты: «Тикет запускается только когда все его блокеры смерджены в `main`».
Пункт про гейтвей: тикеты #2 вливаются в `release/gateway`, а в `main` она идёт одним PR в конце.

По букве правил зависимый тикет гейтвея нельзя начать до финального мерджа. Агент выходит из тупика как умеет: так появилась `integration/gateway-6-7`, хотя правило рядом запрещает новые интеграционные ветки.

Исправление (одна строка):

> Тикет запускается только когда все его блокеры смерджены в целевую ветку: `main`, а для тикетов гейтвея (#2) — `release/gateway`.

Шире: если накопительные ветки будут и для следующих слоёв, сформулировать правило один раз для любой `release/*`, а не отдельным абзацем про #2.

## 2. Правила в тексте агенты нарушают — закреплять механически

Наблюдение: интеграционную ветку завели почти сразу после правила «не создавай», worktree агентов остаются брошенными. Работает надёжно только то, что закреплено механикой (защита `main`, запрет `gh pr merge` в `.claude/settings.json`).

Что можно перевести из текста в механику:
- Имена веток. Pre-push хук (через `make hooks`) или CI-джоб, который отклоняет ветки вне разрешённых шаблонов (например `ticket-*`, `docs/*`, `fix/*`, `release/*`, `sync/*`). Тогда `integration/*` просто не запушится.
- Целевая ветка PR. CI-проверка: PR с `Closes #N` / ссылкой на тикет гейтвея должен идти в `release/gateway`, а не в `main` (пока накопительная ветка жива).
- Уборка worktree. В инструкции агенту (или скилле) — шаг «после открытия PR: `git worktree remove`», плюс цель `make clean-worktrees`, которая удаляет worktree, чьи ветки уже влиты.

Новые абзацы в `CLAUDE.md` вместо этого не добавлять: файл и так длинный, а каждое новое правило читается хуже предыдущих.

## 3. Финальный PR `release/gateway` → `main`

К концу гейтвея ветка накопит 13 тикетов и тысячи строк. Такой PR по существу не отревьюить.

Решить заранее:
- Финальный PR — формальный: ревью уже прошло в PR каждого тикета, в описании просто список влитых PR и итог `make check` + `docker compose up`. Записать это в правило, чтобы никто не пытался ревьюить его целиком.
- Для следующих слоёв подумать, нужна ли накопительная ветка вообще. Альтернатива: вливать тикеты в `main` по одному, а недоделанную функциональность держать невключённой (не подключена в роутер / флаг в конфиге). Меньше merge-рисков и нет противоречия из п. 1.

## 4. CI не запускается на push в `release/gateway`

`.github/workflows/check.yml`: `push` только для `main`. PR в `release/gateway` проверяются, но если в неё что-то попадёт пушем (у владельца есть обход защиты), CI промолчит.

Исправление: `push: branches: [main, 'release/**']`.

## 5. Тесты пакета `provider`

У `app/internal/provider` нет собственных тестов, перевод форматов Claude (`claude_translate.go`, ~250 строк, `claude_stream.go`) проверяется только через тесты `server`.
После #6 (tool calling через оба провайдера) это самое хрупкое место: таблица unit-тестов «запрос OpenAI-формата → запрос Claude» и «события стрима Claude → чанки OpenAI», включая tool calls, ошибки и обрывы стрима.

`config` и `chatwire` без тестов — низкий приоритет, достаточно тестов на разбор конфига с невалидными значениями.
