# Спека: каркас репозитория и ограждения (слой 0)

> Статус: черновик, готов к публикации через `/to-spec`. Выполняется ПЕРЕД спекой гейтвея (спека гейтвея блокируется этой).

## Problem Statement

Весь код проекта пишет агент, а я его ревьюю. Пока в репозитории нет автоматических проверок, любая ошибка агента доходит до моего ревью, и я ловлю глазами то, что мог бы поймать машина. Решения о стеке (Go, без агентских фреймворков) существуют только как договорённость, и ничто не мешает агенту их нарушить.

## Solution

Репозиторий с работающим каркасом Go-проекта и набором ограждений: одна команда проверки, которая падает на нарушении правил, одинаково локально, в pre-commit хуке и в CI. Правила, которые можно проверить машиной, проверяются машиной. Правила-суждения записаны в отдельном файле стандартов для ревью-агента, а требование объяснить ядро перед мерджем закреплено в шаблоне PR.

## User Stories

1. As a разработчик, I want одну команду проверки (линтер, vet, тесты с детектором гонок), so that я одинаково проверяю код везде
2. As a разработчик, I want, чтобы та же команда запускалась в git-хуке перед коммитом, so that плохой код не попадал в коммит
3. As a разработчик, I want, чтобы та же команда запускалась в CI на каждом PR, so that мердж плохого кода был невозможен
4. As a владелец проекта, I want, чтобы импорт агентских фреймворков (LangChain-подобных) приводил к падению линтера, so that решение «без фреймворков» держалось само
5. As a владелец проекта, I want, чтобы игнорирование ошибок и их возврат без контекста ловились линтером, so that в ядре не оседали немые сбои
6. As a владелец проекта, I want, чтобы вывод в stdout вне точки входа ловился линтером, so that логирование шло только через структурный логгер
7. As a ревьюер, I want файл стандартов с правилами-суждениями, so that `code-review` проверял то, что линтер проверить не может
8. As a ревьюер, I want шаблон PR с блоком «пояснение и вопросы для самопроверки», so that для ядра я мог объяснить код перед мерджем
9. As a агент, I want короткий `CLAUDE.md` с указателями на стандарты, глоссарий, ADR и локальные модели, so that я находил нужное без поиска
10. As a агент, I want видеть команду проверки в одном известном месте, so that я запускал её перед каждым PR
11. As a разработчик, I want пустой, но собираемый каркас сервиса и один проходящий тест, so that ограждения проверялись на живом коде
12. As a разработчик, I want, чтобы `docker compose up` поднимал Redis и пустой сервис с рабочими эндпоинтами live и ready, so that запуск был воспроизводим с первого дня
13. As a проверяющий проект, I want видеть историю мелких осмысленных коммитов, so that понимать, как идёт работа

## Implementation Decisions

- Каркас: один Go-модуль, одна точка входа сервиса, структурное логирование через `slog`, лицензия MIT, публичный репозиторий.
- Одна команда проверки (имя выбирает реализация, фиксируется в `CLAUDE.md`): `go vet`, `golangci-lint`, `go test -race`. Хук и CI вызывают именно её, правила не дублируются в трёх местах.
- Хук перед коммитом лежит в версионируемой папке `.githooks/` и включается через `core.hooksPath`. Инструмент `pre-commit` не используется, новых зависимостей нет. Хук только вызывает команду проверки.
- Механические правила живут в конфигурации линтера: запрет импорта агентских фреймворков (депгард со списком запрещённых), проверка обёртывания ошибок, запрет вывода в stdout вне точки входа, проверка неотловленных ошибок.
- Правила-суждения живут только в `CODING_STANDARDS.md`: тесты ходят через HTTP-шов, Redis в тестах настоящий, интерфейс провайдера остаётся маленьким, ядро изменяется с пояснением в PR.
- Шаблон PR содержит блоки: что и зачем, как проверено, пояснение (для ядра) и 3–5 вопросов для самопроверки.
- Стартовые `CLAUDE.md`, `GLOSSARY.md`, ADR берутся из папки-заготовки без изменений по существу.
- Docker Compose поднимает Redis и собираемый пустой сервис (только эндпоинты live и ready), у обоих лимиты памяти (ограничение 16 ГБ машины). Позже гейтвей заменит пустой сервис.

## Testing Decisions

- Хороший тест проверяет внешнее поведение. Для каркаса проверяется сама работоспособность ограждений.
- Единственный шов каркаса — сама команда проверки. Кроме неё есть один smoke-тест сервиса (live отвечает).
- Проверка ограждений: намеренно сломанный пример (запрещённый импорт, проигнорированная ошибка, вывод в stdout) должен давать красный результат команды проверки; исправленный — зелёный. Проверяется один раз при настройке, результат фиксируется в описании PR.
- Хук и CI проверяются тем же способом: PR с нарушением не проходит.
- Prior art: в репозитории пока нет кода.

## Out of Scope

- Гейтвей и любые продуктовые функции (спека гейтвея идёт следом).
- Настройка деплоя и облака.
- Включение защиты ветки `main` (см. Further Notes).
- Дашборды Grafana.
- Настройка Ralph loop (отдельная спека после каркаса, когда команда проверки уже работает и может служить критерием остановки цикла).

## Further Notes

- Команда проверки нужна для Ralph loop как критерий «готово»: цикл останавливается, когда она зелёная.
- Порядок: `/setup-matt-pocock-skills` (сделано) → эта спека → спека гейтвея.
- Защита `main` с обязательной проверкой CI — настройка GitHub, не код. Включается отдельным шагом через `gh api` после первого зелёного прогона CI (раньше обязательной проверки не существует). До этого работаем PR-ами по дисциплине.
