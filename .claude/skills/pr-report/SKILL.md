# PR-отчёт

Владелец проекта ревьюит код, который пишет агент, и перед мерджем ядра должен объяснить его своими словами (Q19). Читать для этого diff и логи сессии неудобно, а журналы агента запрещено коммитить в репозиторий. Этот скилл собирает то, что нужно для ревью, на одну страницу вне репозитория.

Вход: номер PR (если не указан, возьми PR текущей ветки: `gh pr view`). Отчёт строится только по git и `gh`, поэтому работает и в свежей сессии. Если скилл вызван в конце той же сессии, где шла работа, добавь то, чего нет в git: что пробовалось и где агент застрял.

## Сбор данных

Работай через `gh` и `git`, не меняя рабочее дерево (в нём могут идти параллельные сессии: не переключай ветки, не коммить).

- PR: `gh pr view N --json number,title,body,state,baseRefName,headRefName,closingIssuesReferences,statusCheckRollup,reviews,comments,files,additions,deletions`
- Связанный issue: его критерии приёмки. Возьми из `closingIssuesReferences`, при пустом списке из строки `Closes #N` в описании.
- Diff: `gh pr diff N`. Читай код, не только статистику.
- Проверки: `statusCheckRollup`.

## Структура страницы

Порядок важен: самое нужное для решения о мердже стоит сверху.

1. **Шапка.** Номер и название PR, ссылка, статус проверок, размер: строки кода, тестов и служебных файлов (`go.sum`, yaml, документы) раздельно. Если размер выше ориентира проекта, скажи об этом прямо.
2. **Правки правил, а не кода.** Всё, что агент изменил помимо логики продукта: `CLAUDE.md`, `CODING_STANDARDS.md`, `docs/adr/`, `.golangci.yml`, `.github/`, `Makefile`, `scripts/`, `Dockerfile`, `compose.yaml`, шаблоны. Для каждого файла: что было, что стало, чьё это ограничение и ослабляет ли правка правило. Это главный риск: агент может подогнать правила под свой код. Если таких правок нет, напиши «нет».
3. **Что сделано.** Пройди по критериям приёмки issue: каждый критерий, чем подтверждён (тест, проверка), выполнен или нет. Не пересказывай заголовок PR.
4. **Как устроено.** Короткая схема потока запроса через изменённый код и пояснение: что делает код, почему так, что сломается без ключевой части. Опирайся на код, а не только на описание PR.
5. **Вопросы для самопроверки.** 3–5 вопросов, ответы скрыты в раскрывающемся блоке, чтобы владелец сначала ответил сам. Возьми вопросы из описания PR; если их нет или они слабые, напиши свои и пометь «вопросы составлены автором отчёта». Ответы проверь по коду, не по описанию.
6. **Находки ревью.** Замечания из `reviews` и `comments` и что с ними стало (исправлено, отклонено, открыто). Если ревью не было, так и напиши.
7. **Риски и непроверенное.** Что не покрыто тестами, какие допущения принял агент, что отложено, какие проверки зелёные только потому, что ничего не проверяют (например, пакеты без тестов). Только то, что нашёл сам; не придумывай риски для заполнения раздела.

## Правила честности

Отчёт читают, чтобы решить, мерджить ли. Поэтому не смягчай: невыполненный критерий называй невыполненным, непроверенное называй непроверенным. Не пиши «всё хорошо», если ты не прочитал код. Если чего-то не смог узнать (нет доступа к логам CI), укажи это в отчёте.

## Публикация

1. Загрузи скилл `artifact-design` перед написанием страницы и следуй его контракту. Страницу пиши как один HTML-файл в каталог scratchpad, не в репозиторий.
2. Публикуй Artifact приватным, заголовок вида «PR #N: короткое название».
3. Не включай в страницу секреты, значения переменных окружения и содержимое глобального `~/.claude/CLAUDE.md`. Репозиторий публичный, страница должна быть безопасна для пересылки.
4. В ответе дай ссылку и три строки сути: что сделано, что нужно проверить в первую очередь, мерджить можно или нет. Ссылку в комментарий к PR добавляй только если пользователь попросит.
