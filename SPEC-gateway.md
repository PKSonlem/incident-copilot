# Спека: LLM-гейтвей (слой 1 Incident Copilot)

> Статус: черновик. В трекер НЕ опубликован, метка `ready-for-agent` не поставлена: трекер не настроен (нужен `/setup-matt-pocock-skills`).

## Problem Statement

Агентам Incident Copilot (и любому другому клиенту) нужно вызывать LLM, и при этом они не должны знать, какой провайдер за ним стоит, сколько это стоит и что будет при его сбое. Сейчас единой точки входа нет. Если каждый воркер ходит в Claude или в локальную модель сам, нет общего кэша, нет защиты от лавины запросов и перерасхода бюджета, нет fallback при недоступности провайдера и нет картины «сколько токенов и денег ушло на какое расследование». Локальные модели слабые (контекст 16k), и без маршрутизации их приходится либо не использовать вовсе, либо назначать вручную в каждом месте кода.

## Solution

Отдельный сервис-гейтвей с OpenAI-совместимым HTTP API. Клиент отправляет обычный запрос chat completions и получает ответ (в том числе потоком SSE), не зная, кто его породил. Гейтвей сам решает, куда отправить запрос (Claude или локальная модель), отдаёт ответ из кэша, если такой запрос уже был, ограничивает частоту запросов, переключается на запасной провайдер при сбое и считает токены и стоимость каждого запроса. Всё это видно в метриках, логах и трейсах и готово к выводу на Grafana-дашборд.

## User Stories

1. As a разработчик агента, I want отправлять запросы в одну точку по OpenAI-совместимому API, so that мой код не зависит от конкретного провайдера
2. As a разработчик агента, I want получать ответ потоком (SSE), so that пользователь видит ход рассуждения сразу, а не после полной генерации
3. As a разработчик агента, I want получать обычный (не потоковый) ответ, so that простые вызовы вроде классификации не требуют обработки потока
4. As a разработчик агента, I want передавать в запросе tools и получать от модели вызовы tools, so that цикл агента работает через гейтвей без потери функциональности
5. As a разработчик агента, I want пометить запрос как простой или сложный, so that гейтвей отправил его на подходящую по цене модель
6. As a разработчик агента, I want получать понятную ошибку, если запрос не помещается в контекст выбранной модели, so that я знаю, что нужно сократить вход
7. As a владелец сервиса, I want, чтобы повторный одинаковый запрос отдавался из кэша без обращения к провайдеру, so that я не плачу дважды за один и тот же ответ
8. As a владелец сервиса, I want, чтобы кэш учитывал модель, параметры и содержимое запроса, so that ответ от другой конфигурации не был ошибочно отдан из кэша
9. As a владелец сервиса, I want, чтобы запись в кэше имела срок жизни, so that устаревшие ответы не живут вечно
10. As a владелец сервиса, I want видеть в ответе признак попадания в кэш, so that я мог отладить поведение и посчитать hit rate
11. As a владелец сервиса, I want, чтобы потоковые ответы из кэша отдавались тоже потоком, so that клиенту не нужно различать два случая
12. As a владелец сервиса, I want ограничивать число запросов в единицу времени на каждый API-ключ, so that один клиент или зациклившийся воркер не съел весь бюджет
13. As a клиент, I want получать 429 с указанием, когда можно повторить, so that я могу корректно сделать паузу
14. As a владелец сервиса, I want, чтобы лимиты работали одинаково при нескольких экземплярах гейтвея, so that горизонтальное масштабирование не ломает защиту
15. As a владелец сервиса, I want, чтобы при ошибке или таймауте основного провайдера запрос автоматически уходил на запасной, so that временный сбой не ломает расследование
16. As a владелец сервиса, I want, чтобы повтор на запасной провайдер не происходил для ошибок клиента (неверный запрос), so that мы не тратим деньги на заведомо плохие запросы
17. As a владелец сервиса, I want видеть, какой провайдер реально ответил, so that я понимаю, когда работал fallback
18. As a владелец сервиса, I want, чтобы после нескольких подряд сбоев провайдер временно исключался из маршрутизации, so that мы не тратим время на заведомо мёртвый вариант
19. As a владелец сервиса, I want считать входные и выходные токены каждого запроса, so that я знаю реальный расход
20. As a владелец сервиса, I want считать стоимость каждого запроса по таблице цен моделей, so that я видел деньги, а не только токены
21. As a владелец сервиса, I want, чтобы запросы к локальной модели имели нулевую или отдельно заданную стоимость, so that экономия от маршрутизации была видна в цифрах
22. As a разработчик, I want группировать расход по идентификатору расследования, so that я вижу, во сколько обошёлся каждый инцидент
23. As a владелец сервиса, I want задать месячный или дневной бюджет на ключ и получать отказ при превышении, so that баг не сожжёт деньги
24. As a оператор, I want метрики в формате Prometheus (запросы, латентность, токены, стоимость, hit rate кэша, fallback, ошибки), so that я построил дашборд в Grafana
25. As a оператор, I want структурные логи каждого запроса без самого текста промпта по умолчанию, so that в логах не оседают чувствительные данные
26. As a оператор, I want трейсы запроса через OpenTelemetry (кэш, выбор провайдера, вызов провайдера), so that я вижу, где потрачено время
27. As a оператор, I want эндпоинты проверки живости и готовности, so that оркестратор контейнеров знает состояние сервиса
28. As a оператор, I want конфигурацию провайдеров, моделей, цен и лимитов в одном файле и переменных окружения, so that менять их можно без перекомпиляции
29. As a оператор, I want, чтобы секреты (ключи провайдеров) читались только из окружения, so that они не попали в репозиторий
30. As a разработчик, I want подключать нового провайдера, реализовав один небольшой интерфейс, so that добавление не затрагивает остальной код
31. As a разработчик, I want запускать гейтвей со всеми провайдерами, подменёнными фейками, so that тесты были быстрыми, бесплатными и детерминированными
32. As a пользователь локальных моделей, I want подключать любой OpenAI-совместимый сервер (`llama-server`, `llama-swap`) по адресу, so that не зависеть от Ollama
33. As a пользователь с 16 ГБ памяти, I want задать лимит параллельных запросов к локальной модели, so that сервер не захлебнулся
34. As a владелец сервиса, I want, чтобы гейтвей корректно завершал текущие запросы при остановке, so that развёртывание не обрывает ответы
35. As a клиент, I want получать ошибки в OpenAI-совместимом формате, so that стандартные клиентские библиотеки их понимают
36. As a проверяющий проект (интервьюер), I want прочитать README с диаграммой гейтвея и таблицей решений, so that понять, зачем нужна каждая часть
37. As a разработчик, I want, чтобы весь стенд гейтвея (сам гейтвей, Redis, метрики) поднимался одной командой docker compose, so that демо воспроизводимо
38. As a владелец сервиса, I want, чтобы отмена запроса клиентом прерывала запрос к провайдеру, so that мы не платим за ответ, который никто не прочитает

## Implementation Decisions

- Гейтвей — отдельный сервис на Go. Внешний контракт — OpenAI-совместимый chat completions (обычный режим и потоковый SSE, включая tools).
- Провайдеры скрыты за одной небольшой абстракцией. В MVP два вида: Claude (гейтвей сам переводит запрос и ответ в формат Anthropic и обратно) и любой OpenAI-совместимый локальный сервер (`llama-server` / `llama-swap`, текущий адрес `localhost:7382`). Ollama как отдельный провайдер не нужен.
- Кэш: точное совпадение. Ключ строится из модели, параметров генерации и содержимого сообщений. Хранилище — Redis, у записей есть TTL. Семантический кэш не входит в эту спеку (см. Out of Scope).
- Rate limit на API-ключ, состояние в Redis, чтобы лимит работал при нескольких экземплярах. Ответ при превышении — 429 с заголовком о времени повтора.
- Бюджет на ключ (дневной или месячный) проверяется перед запросом, при превышении возвращается отказ в OpenAI-совместимом формате.
- Fallback: цепочка провайдеров на каждый тип запроса. Повтор на запасной — только для ошибок провайдера и таймаутов, не для ошибок клиента. Простой circuit breaker временно исключает провайдера после серии сбоев.
- Маршрутизация: клиент помечает запрос как простой или сложный (подсказка о сложности, как поле или заголовок запроса). Простые идут на локальную модель, сложные на Claude. Если вход не помещается в контекст локальной модели (16k для текущих профилей), гейтвей не отправляет запрос туда и поступает по правилу, заданному конфигурацией (направляет на Claude или возвращает ошибку клиенту).
- Учёт: токены вход и выход берутся из ответа провайдера (при потоке из финального события), стоимость считается по таблице цен в конфигурации. Расход агрегируется по API-ключу и по идентификатору расследования, который клиент передаёт заголовком.
- Ограничение параллелизма на каждого провайдера, особенно на локального, настраивается в конфигурации.
- Наблюдаемость: метрики Prometheus (запросы, латентность, токены, стоимость, hit rate кэша, fallback, отказы по лимитам), структурные логи через `slog` без текста промптов по умолчанию, трейсы OpenTelemetry. Эндпоинты live и ready.
- Конфигурация: файл (провайдеры, модели, цены, лимиты, цепочки) + переменные окружения для секретов. Секреты в репозиторий не попадают.
- Отмена запроса клиентом прерывает исходящий запрос к провайдеру. При остановке сервис дожидается текущих запросов.
- Запуск: docker compose с гейтвеем, Redis и метриками, с лимитами памяти (из Q26).

## Testing Decisions

- Хороший тест проверяет только внешнее поведение гейтвея через его HTTP API, а не устройство внутренних пакетов. Тесты не должны ломаться при рефакторинге внутренностей.
- Единственный шов — HTTP API гейтвея (решение пользователя). Клиент в тесте — обычный HTTP-клиент. Вместо реальных провайдеров стоят фейковые HTTP-серверы, которыми тест управляет: могут отвечать нормально, с ошибкой, с задержкой, потоком, считать полученные запросы.
- Через этот шов проверяются: кэш (второй одинаковый запрос не доходит до фейка), TTL, rate limit (429 после лимита), бюджет, fallback (ошибка первого фейка, ответ от второго), отсутствие повтора на ошибках клиента, circuit breaker, маршрутизация простых и сложных запросов, обработка слишком длинного входа, потоковые ответы, tools, учёт токенов и стоимости, отмена запроса клиентом, формат ошибок.
- Redis в тестах настоящий (поднимается на время тестов), а не мок, потому что поведение лимитов и кэша зависит от него.
- Тесты утверждаются пользователем до начала реализации (TDD, из Q21).
- Реальные модели в этих тестах не вызываются. Проверка с реальными провайдерами — отдельный ручной запуск.
- Prior art: в репозитории пока нет кода, прецедентов нет.

## Out of Scope

- Агент с tool calling, оркестратор воркеров, RAG, сценарии хаоса, стенд Prometheus/Loki и демо-сервис (другие спеки).
- Семантический кэш (по близости эмбеддингов).
- Веб-интерфейс и админка (фронтенд — v2).
- Полноценная система пользователей и биллинга: достаточно API-ключей с лимитами и бюджетом.
- Дообучение, оценка качества ответов, eval (отдельный слой).
- Создание Grafana-дашборда как артефакта (метрики для него входят в спеку, сам дашборд нет).

## Further Notes

- Допущения, которые стоит подтвердить на этапе интервью перед реализацией: (1) подсказка сложности передаётся клиентом, а не определяется гейтвеем автоматически; (2) для слишком длинного входа по умолчанию запрос уходит на Claude; (3) бюджет считается за сутки, а не за месяц; (4) стоимость локальной модели берётся как ноль, а условная цена по электричеству не считается.
- Соответствие решениям: ADR 0001 (без фреймворков, прямые вызовы API), ADR 0003 (локальный OpenAI-совместимый сервер, маршрутизация), ADR 0002 (фейковые провайдеры, один шов), `CODING_STANDARDS.md` (процесс ревью), лимиты памяти в docker compose.
- Список «открытых допущений» важнее, чем остальная часть: если хоть одно из них неверно, поменяется контракт гейтвея.
